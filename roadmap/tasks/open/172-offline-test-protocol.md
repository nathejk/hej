# 172 — Offline test protocol on real devices

**Status:** open
**Priority:** medium
**Created:** 2026-08-31

## Prerequisite: a device cannot reach the dev stack today

This task was written assuming a phone could open the app. It cannot, and that has to be
solved before any of the criteria below can be attempted.

`hej.local.nathejk.dk` resolves to **127.0.0.1** — a public DNS record pointing at loopback, so
Traefik can hold a real `desec` certificate for a local hostname. That works perfectly on the
developer's machine and is unreachable from anything else: from a phone, `127.0.0.1` is the
phone.

And `http://<LAN-IP>` is not a fallback. Every feature this task exists to verify needs a
**secure context**: service worker, install to home screen, cache eviction, geolocation. The
`localhost` exemption does not apply to another device on the network, so plain HTTP gives a
browser that cannot install and cannot register a worker — i.e. nothing to test.

Three ways out, in the order I would try them:

| Approach | Trade-off |
|---|---|
| **Tailscale** (funnel or a tailnet hostname) | Phone joins the tailnet, real HTTPS, no router or DNS work. Best if the device can install Tailscale. |
| **Tunnel** (`cloudflared`, `ngrok`) | Public HTTPS URL to the local Traefik in one command. Watch the BFF's cookie flags and `allowedHosts` in `vite.config.ts` — a new hostname has to be admitted there. |
| **LAN DNS override** — point `*.local.nathejk.dk` at the machine's LAN IP on the router | Closest to production and keeps the desec cert valid; needs router control and works on that network only. |

Whichever is chosen, **record it here** — the next person to run this protocol will hit the
same wall, and "how do I open this on a phone" is not obvious from the compose file.

Note also that a *dev* stack is not a faithful subject for the eviction and install tests: the
service worker is only generated by a production build (`vite build`, `generateSW`), so
verifying install and cache behaviour means serving `dist/` — the `prod` target, or a staging
host. Testing against the Vite dev server would produce a pass that means nothing, because
there is no service worker in dev at all.

## Description

PRD 007's success metrics require verification **by test on a real device, not by
assumption** — the pane's whole premise is behaviour under conditions a desktop browser
does not reproduce.

Two halves, and they must not be conflated:

- The **directory works with the radio off** — list, groups, search, favourites,
  profiles, portraits.
- The **patrol lookup fails clearly** with the radio off — "kræver forbindelse" and a
  pointer to the radio, never an empty or stale patrol.

Cover both iOS/iPadOS Safari 16.4+ (home-screen install) and Chrome 111+ on Android, per
the `.rules` baseline. iOS specifically, because that is where cache eviction bites and
where the install path differs.

Also worth exercising in the same pass: launch after several days unused (eviction), and
airplane mode toggled mid-session (reconnect triggering a version check, task 162).

## Acceptance Criteria

- [ ] **Device access solved and recorded above** — tunnel, tailnet or LAN DNS — including any
      `allowedHosts` or cookie-flag changes it needed.
- [ ] Tested against a **production build**, not the dev server: the service worker only exists
      in `generateSW` output, so install and eviction cannot be observed otherwise.
- [ ] A written protocol in this file: device, OS version, install method, steps. *Partly satisfied
      by reference: **`roadmap/offline-test-protocol.md`** (task 195) now carries the shared steps —
      radio off, names-without-faces, OS-cleared cache, persistence, full origin — and points back
      here for the device-access prerequisite and the stale-install trap. What is still owed *here* is
      the pane-specific half: the patrol lookup refusing offline, and the run's actual results.*
- [ ] Directory verified fully usable offline on both platforms, installed to home
      screen.
- [ ] Patrol lookup verified to fail clearly offline on both platforms.
- [ ] Eviction scenario exercised: cache cleared → pane degrades to names-only, then
      recovers on reconnect.
- [ ] Reconnect triggers a freshness check without a manual action.
- [ ] Results recorded in the progress log, including anything that surprised us.
- [ ] The stale-install trap is accounted for in the protocol: with `registerType: 'prompt'` an
      installed app keeps its old bundle until the update prompt is accepted, so every step
      needs to state which build the device is actually running. A test that silently exercised
      yesterday's bundle would pass and mean nothing. (Documented in the `docker-dev-stack`
      skill, 2026-09-01, after it cost exactly that confusion.)
